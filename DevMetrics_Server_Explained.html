1. High-Level Overview

The DevMetrics server is an Express.js backend that acts as a secure proxy between the React frontend and the GitHub API. It handles OAuth authentication, fetches developer data from multiple GitHub endpoints, computes advanced analytics metrics, and returns an aggregated JSON response to the dashboard.

Frontend React + Vite SPA → sends requests to /auth/* and /api/github/*
↕
Express Server Session management, CORS, routing, caching
↕
GitHub APIs REST API v3 + GraphQL v4 + Search API

3. Authentication Routes — server/routes/auth.js

Implements the GitHub OAuth 2.0 Authorization Code Flow:

User clicks Sign In → GET /auth/github → Redirect to GitHub → User authorizes → GitHub callback with code → Exchange for token → Store in session → Redirect to dashboard

3.1 All Endpoints

MethodEndpointDescription
GET /auth/github Redirects user to GitHub's OAuth page. Requests scopes: read:user, user:email, repo (includes private repos)
GET /auth/github/callback Receives the authorization code from GitHub.
1. Exchanges code for an access token
2. Fetches the user's GitHub profile
3. Stores token + user in the server-side session
4. Redirects to /dashboard
GET /auth/me Returns the logged-in user's profile from the session, or 401 if not authenticated
POST /auth/logout Destroys the session and clears the connect.sid cookie

3.2 User Data Stored in Session

req.session.user = {
  login,      // GitHub username
  name,       // Display name
  avatarUrl,  // Profile picture URL
  bio,        // User bio
  publicRepos,// Public repo count
  followers,  // Follower count
  following,  // Following count
  createdAt,  // Account creation date
  htmlUrl,    // GitHub profile link
}
🔒 Security Note

The access token is never sent to the frontend. It stays server-side in the session store. The frontend only receives the user profile data via /auth/me.

4. GitHub Stats Route — server/routes/github.js

This is the core of the application — a single GET /api/github/stats endpoint that aggregates data from 8+ GitHub API calls and computes rich developer analytics.

Endpoint Summary

GET /api/github/stats — Requires an authenticated session. Returns a comprehensive JSON payload with user profile, repository stats, activity data, and computed impact metrics.

Optional query param: ?nocache=1 to bypass cache.

5. Caching System

To solve the "slow loading" problem caused by many GitHub API calls, the server uses an in-memory cache:

PropertyValue
StorageJavaScript Map (in-memory, per-process)
Cache KeyGitHub username
TTL (Time To Live)5 minutes
Stale CleanupEntries older than 30 minutes are purged on each write
BypassAdd ?nocache=1 query parameter
Debug EndpointGET /api/github/clear-cache
Cache HeaderX-Cache: HIT or X-Cache: MISS
⚠️ Limitation

Since the cache is in-memory, it is lost on server restart and is not shared across multiple server instances. This is fine for single-instance deployments.

6. Data Fetching Strategy

The stats endpoint fires 8 API calls in parallel using Promise.all to minimize latency:

#API CallWhat It Fetches
1 GET /user/repos All repos (owned + collaborator + org member), up to 100, sorted by last update. Includes private repos.
2 GET /users/{login}/events Last 100 public events (pushes, PRs, issues, reviews, etc.)
3 GET /search/commits User's 100 most recent commits (via Search API)
4 POST /graphql Contribution calendar (the green squares) — 52 weeks of daily contribution counts
5 GET /search/issues PRs reviewed by the user (not authored)
6 GET /search/issues Issues the user commented on (not authored)
7 GET /search/issues PRs authored by the user (total count)
8 GET /search/issues PR review comments on others' PRs

6.1 Contribution Calendar Fallback

If the GraphQL query fails (e.g., token doesn't have the right scope), the server builds a fallback contribution calendar from the events and search commits data — constructing 52 weeks of daily counts manually.

6.2 Individual Commit Detail Fetch

Why fetch commits individually?

The /search/commits endpoint does not return line-level stats (additions/deletions). To calculate code churn, quality, and complexity, the server fetches up to 30 commits individually via their API URLs using Promise.allSettled (so one failure doesn't break the rest).

7. Computed Metrics Deep Dive

7.1 Code Churn Analysis

Measures the rate of code being written vs. deleted over time.

MetricFormula / Description
Total AdditionsSum of all lines added across analyzed commits
Total DeletionsSum of all lines removed across analyzed commits
Net Code Changeadditions - deletions
Churn Rate(deletions / additions) × 100% — lower means more code retained
Code Retention(netChange / additions) × 100% — how much code survives
Avg Lines/Commit(additions + deletions) / commitCount
TimelineDaily breakdown of additions, deletions, and net change (last 14 entries)

7.2 Commit Quality Scoring

Each commit is scored 0–100 based on multiple factors:

FactorScore Impact
Commit Size (Goldilocks Zone) • 0 lines (empty): −30
• <5 lines (trivial): −15
• 20–500 lines (ideal): +25
• >1000 lines (bulk): +10
Message Quality • <10 chars (lazy): −10
• 30–100 chars (descriptive): +15
AI-Pattern DetectionKeywords like "copilot", "auto-generated" + <10 lines: −20
Problem-Solving Keywords"refactor", "optimize", "implement", etc. + ≥10 lines: +20
Add/Delete BalanceBalanced changes (ratio >0.3) + ≥50 lines: +10

Quality Grades

≥75 → Excellent ≥60 → Good ≥45 → Fair Below → Needs Improvement

7.3 Authenticity Score (Anti-AI Noise)

Starts at 100 and adjusts based on signals:

SignalEffect
High trivial commit ratio−40 × trivialRatio
High suspicious commit ratio−30 × suspiciousRatio
Quality score ≥ 70+10
Quality score ≥ 55+5
>50% commits have good messages (≥30 chars)+5
Balanced add/delete ratio (>0.2)+5
Meaningful commit ratio ≥ 80%+5

Authenticity Grades

≥85 → Verified ≥70 → Likely Authentic ≥50 → Mixed Signals Below → Review Needed

7.4 Collaboration Score

A weighted composite of community participation:

collaborationScore = (prReviewCount × 1)
                   + (prCommentCount × 0.5)
                   + (issueCommentCount × 0.3)
                   + (prAuthoredCount × 0.2)

7.5 Review Depth

MetricDescription
Total ReviewsNumber of PRs reviewed (all-time, via Search API)
Review CommentsHigher of Search API count or event-based count
Issues HelpedIssues commented on (excluding self-authored)
Avg Reviews/WeektotalReviewActivity / min(accountAgeWeeks, 52)
Helpfulness Score(reviews × 3) + (prComments × 2) + (issueComments × 1.5) + (recentEvents × 0.5)

7.6 Complexity Trends

For each day with commits, tracks:

  • Avg lines changed per commit
  • Number of files touched
  • Complexity level: High (>300 lines), Medium (100–300), Low (<100)

Returns the last 14 data points for trend visualization.

7.7 Private Work Summary

Aggregates statistics specifically for private repositories:

  • Total private vs. public repo count and percentage
  • Stars and forks on private repos
  • Top 5 languages used in private repos
  • 3 most recently active private repos
  • Total size of private repos

7.8 Impact Score (The Big Number)

A composite 0–100 score representing overall developer impact:

ComponentWeightNormalization
Commit Quality30%Raw quality score (0–100)
Code Retention20%Retention percentage (0–100)
Collaboration20%min((collaborationScore / 30) × 100, 100)
Authenticity15%Raw authenticity score (0–100)
Consistency15%min((activeDays / totalDays) × 200, 100)
impactScore = (quality × 0.30) + (retention × 0.20)
            + (collaboration × 0.20) + (authenticity × 0.15)
            + (consistency × 0.15)

8. Final Response Structure

The /api/github/stats endpoint returns this JSON structure:

{
  user: {                    // GitHub profile
    login, name, avatarUrl, bio, publicRepos,
    followers, following, createdAt, htmlUrl
  },
  stats: {                   // Repository aggregates
    totalStars, totalForks, forkedRepos, totalRepos,
    publicRepos, privateRepos, totalWatchers,
    totalOpenIssues, topLanguages
  },
  recentRepos: [...],        // 6 most recently updated repos
  activityTimeline: [...],   // Last 14 days of event counts
  contributionCalendar: {    // Green squares grid
    totalContributions,
    weeks: [{ contributionDays: [...] }]
  },
  eventTypes: [...],         // Top 6 event types by count
  impactMetrics: {
    codeChurn: {...},        // Additions, deletions, churn rate, timeline
    collaboration: {...},    // Reviews, comments, PRs authored
    quality: {...},          // Score, grade, patterns, distribution
    authenticity: {...},     // Score, grade, signals
    reviewDepth: {...},      // Reviews, helpfulness, avg/week
    complexityTrends: [...], // Daily complexity data points
    privateWork: {...},      // Private repo summary
    impactScore: 0-100       // The overall number
  },
  _cache: {                  // Cache metadata
    hit: boolean, cachedAt, ttl, age
  }
}

Summary

The server is a stateful Express.js backend that authenticates users via GitHub OAuth, maintains sessions with access tokens, and provides a single rich API endpoint (/api/github/stats) that aggregates data from 8+ parallel GitHub API calls. It computes 8 distinct analytics metrics — including code churn, commit quality, authenticity scoring, collaboration depth, and an overall impact score — cached for 5 minutes to optimize performance.
